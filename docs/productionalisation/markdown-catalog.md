# Markdown files a production project needs

The pages that exist today are indexed in
[guides/README.md](../guides/README.md). Agent files are in
[agent-index.md](../agent-index.md). The tree is in
[codebase-index.md](../codebase-index.md).

Code tells the workspace what to create. Markdown tells the next person when
they are allowed to create it, how to undo it, and which choice was
deliberate. The files below are the set. MLOps Stacks generates the first
group. The rest are the operating set this kind of project grows on the
first real deploy.

Write them in the same pull request as the behaviour they describe. A
runbook that lags the YAML is how a teardown deletes the wrong endpoint.

## Minimum set if you are starting from nothing

Create these before the first `bundle deploy`. You can merge the Stacks
names and the operating names; you cannot skip the question each one
answers.

1. `README.md` — local test command and a pointer to deploy docs.
2. `docs/mlops-setup.md` — hosts, principals, variable groups. Here that is [azure-devops.md](../guides/azure-devops.md) plus [secrets.md](../secrets.md).
3. `docs/ml-pull-request.md` — how a training change is tested. Here that is the README score section plus CI.
4. `resources/README.md` or `databricks/README.md` — map of YAML files to jobs. Not a separate file here yet; the map is [folder-structure.md](folder-structure.md) and [required-files.md](required-files.md).
5. `docs/branch-rules.md`
6. `docs/secrets.md`
7. One ADR for "what we will pay for, and what we will not create yet."
8. A cost sheet dated before deploy.
9. A teardown runbook.
10. A promotion runbook, even if staging and prod hosts are blank.
11. Pull request template with "no secrets" and "does this create a cloud resource?"

Add validation, feature, batch, and monitoring READMEs when those
directories exist. An empty README for a folder you do not have yet does
not help.

## What each document must contain

- **README:** the prediction, the install, the test command, the branch names, and the link to the cost gate.
- **Setup:** ordered steps, the name of every secret, and the command that proves auth works (`bundle validate`). No secret values.
- **Pull-request path:** which tests to run, which files a training change touches, and who merges.
- **Resource map:** file → job or endpoint name → target overrides.
- **ADR:** status, date, context, decision, alternatives, consequences. Cost numbers cite the pricing page, not a guess.
- **Runbook:** prerequisites, commands, the check that proves success, and the rollback. One action per step.
- **Changelog:** user-visible changes under `Unreleased`, then moved under a tag when you cut one.

These documents are the production set that is not written as its own file
yet, because the feature is not live:

| Missing page | Write it when |
|---|---|
| `databricks/README.md` resource map | You want reviewers to see job names without reading every YAML |
| Validation README (`Challenger` checks) | A task sets an alias instead of only exiting non-zero |
| Monitoring README | Inference capture or Lakehouse Monitoring is turned on |
| Feature engineering README | A feature table replaces `load_iris` |
| `docs/mlops-setup.md` as one page | A second person has to recreate the Azure DevOps project from scratch |

Until then, the ELI25 guides and the runbooks are the pages to follow.
